# Integrating Cx into a C project

Cx is a thin extension over C: you write `.cx` files using namespaces, RAII
struct destructors, static traits and macros, and `cx` transpiles them to
**portable C** that any normal C toolchain (GCC, Clang, `arm-none-eabi-gcc`, …)
compiles. There is no runtime, no special linker step, and no compiler fork —
the output is plain `.c`.

This guide covers producing C, wiring it into a build, calling between C and Cx,
debugging, and editor setup. The language itself is documented in
[`language.md`](./language.md); implementation details are in
[`technical.md`](./technical.md).

---

## 1. Producing C from Cx

| Command | Purpose |
| :--- | :--- |
| `cx build <file.cx\|file.hx> [-o <out>]` | Transpile one file to C (stdout if `-o` is omitted) |
| `cx expand <file.cx>` | Print the source after `macro_rules!` expansion |
| `cx dump <file.cx>` | Parse and print the AST (debugging) |
| `cx lsp` | Run the language server on stdio |
| `cx --version` | Print the version |

Example:

```sh
cx build src/counter.cx -o build/counter.c
```

### What the generated C looks like

Input `counter.cx`:

```cxc
namespace demo {

    struct Counter {
        int value;

        Counter(int v) {
            value = v;
        }

        ~Counter() {
            reset(value);
        }
    };

    int reset(int v) {
        return v;
    }

    void run() {
        Counter c(1);
    }
}
```

Output `counter.c` (simplified):

```c
/* Generated by cx 0.1.0 from counter.cx. Do not edit. */

struct demo__Counter;
int  demo__reset(int v);
void demo__run(void);
void demo__Counter__ctor(struct demo__Counter *self, int v);
void demo__Counter__dtor(struct demo__Counter *self);

struct demo__Counter {
    int value;
};

void demo__Counter__ctor(struct demo__Counter *self, int v)
{
    self->value = v;
}

void demo__Counter__dtor(struct demo__Counter *self)
{
    demo__reset(self->value);
}

int demo__reset(int v)
{
    return v;
}

void demo__run(void)
{
    struct demo__Counter c __attribute__((cleanup(demo__Counter__dtor)));
    demo__Counter__ctor(&c, 1);
}
```

Two transformations matter to callers:

- **Namespaces → name mangling.** The path is joined with `__`
  (`demo` + `Counter` → `demo__Counter`, `demo` + `run` → `demo__run`). Global
  scope is left untouched. The full table is in
  [`language.md`](./language.md) §13.
- **RAII → `__attribute__((cleanup))`.** Every local whose type has a
  destructor gets the attribute; the destructor runs on every scope exit
  (`return`, `break`, `continue`, `goto`, or falling off the block).

### Compiler requirements

The generated destructors rely on the `cleanup` attribute, which is supported by
**GCC and Clang** (including embedded GCC toolchains). Compile the generated C
with `-std=gnu11` or later. MSVC is not supported.

## 2. Wiring it into a C build

Cx is a pure source-to-source step, so it slots in as a build rule that turns
`.cx` into `.c`; the rest of your toolchain is unchanged.

### Recommended layout

```
project/
├── src/
│   ├── main.c            # hand-written C
│   └── counter.cx        # Cx source
├── build/                # generated .c and .o live here (git-ignored)
└── Makefile
```

### Makefile

```make
CX      ?= cx
CXFLAGS ?=

CC      ?= cc
CFLAGS  ?= -std=gnu11 -O2 -Wall -Wextra

# All Cx sources.
CX_SRC  := $(wildcard src/*.cx)

# Transpiled C (kept in build/, mirrors basenames).
GEN_C   := $(patsubst src/%.cx,build/%.c,$(CX_SRC))
GEN_O   := $(GEN_C:.c=.o)

# Hand-written C.
C_SRC   := src/main.c
C_OBJ   := $(patsubst src/%.c,build/%.o,$(C_SRC))

build/%.c: src/%.cx | build
	$(CX) $(CXFLAGS) build $< -o $@

build/%.o: build/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c $< -o $@

build:
	mkdir -p build

app: $(GEN_O) $(C_OBJ)
	$(CC) $(CFLAGS) $^ -o $@

clean:
	rm -rf build app

.PHONY: clean
```

Because `build/%.c` depends on `src/%.cx`, generated files are only recreated
when the Cx source changes — the transpile step is incremental.

Add the generated C to `.gitignore` (it is a build artifact):

```
/build/
```

### CMake (alternative)

```cmake
set(CX_SRC  src/counter.cx)
set(GEN_C   ${CMAKE_BINARY_DIR}/counter.c)

add_custom_command(
    OUTPUT  ${GEN_C}
    COMMAND cx build ${CMAKE_CURRENT_SOURCE_DIR}/src/counter.cx -o ${GEN_C}
    DEPENDS ${CMAKE_CURRENT_SOURCE_DIR}/src/counter.cx
    COMMENT "Transpiling counter.cx")

add_executable(app src/main.c ${GEN_C})
set_source_files_properties(${GEN_C} PROPERTIES GENERATED TRUE)
set(CMAKE_C_STANDARD 11)
```

## 3. Calling between C and Cx

Within one Cx file, calls "just work" (and are emitted with the mangled name).

From hand-written C, call the mangled name. Given the example above, declare:

```c
/* generated by counter.cx */
void demo__run(void);
int  demo__reset(int v);

int main(void) {
    demo__run();
    return demo__reset(1) - 1;
}
```

Structs are visible by their mangled tag: `struct demo__Counter`. For a stable
C-facing seam, emit a **declaration-only header** with `cx build foo.hx -o foo.h`
(include guard, typedefs, struct definitions, prototypes) and include that from
C. A `.cx` can also pull in another module with `import "mod.hx";`, which parses
the target's declarations and emits `#include "mod.h"`.

The full name-mangling table is in [`language.md`](./language.md) §13. `__` is
the reserved separator: do not use `__` in your own Cx identifiers.

## 4. Debugging and diagnostics

Two things make the generated code feel like first-class source:

- **`#line` directives.** The transpiler injects `#line N "file.cx"` before
  declarations, so compiler warnings/errors and GDB backtraces point at your
  `.cx` file and line — not the generated `.c`.
- **Same diagnostics as the editor.** `cx build` and `cx lsp` share one parser,
  so what the editor flags is exactly what the build flags:
  `file.cx:11:5: error: syntax error, unexpected IDENT, expecting ';'`.

To inspect a parse or an expansion during integration:

```sh
cx dump   src/counter.cx
cx expand src/counter.cx
```

## 5. Current limitations

Integration-relevant limitations (the full list is in
[`roadmap.md`](./roadmap.md) and [`required-features.md`](./required-features.md)):

- **Structs require a trailing `;`** (`};`), exactly like C/C++.
- **Postfix method calls are a first cut.** Chained `a.b().c()` and computed
  receivers are not covered; `Type::func(&x, …)` remains the general spelling.
- **Macros cross `import` boundaries**, but hygiene is not implemented.
- **`cleanup` is GCC/Clang only** (no MSVC).
- **The LSP is same-file for `documentHighlight` / `references` / `rename`**;
  cross-file references and a binding-aware rename are pending.

## 6. Adding the language server

The `cx lsp` subcommand runs a JSON-RPC 2.0 server over stdio. Feature reference:
[`lsp.md`](./lsp.md).

### Neovim (0.11+ / this machine's 0.12)

Register the filetypes and point Neovim at the server:

```lua
-- ~/.config/nvim/init.lua
vim.filetype.add({ extension = { cx = "cx", hx = "cx" } })

vim.lsp.config("cx", {
  cmd = { "cx", "lsp" },
  filetypes = { "cx" },
  root_markers = { "Makefile", ".git" },
})

vim.lsp.enable("cx")
```

Point `cmd` at the built binary (e.g. the absolute path to `./cx`, or a `cx` on
`$PATH`). After rebuilding `cx`, a running server keeps the old binary in memory,
so restart the client — `:LspRestart` — to pick up the new build.

### Syntax highlighting

Cx highlighting is provided by a small Vim syntax file layered on the built-in C
syntax (comments, strings, numbers, types and C keywords come from C):

- `~/.config/nvim/syntax/cx.vim` — highlights `namespace`, struct
  destructors (`~TypeName`), `::`, and the Cx keywords.
- `~/.config/nvim/ftdetect/cx.vim` — maps `*.cx` and `*.hx` to the `cx`
  filetype.

No tree-sitter parser is required.
