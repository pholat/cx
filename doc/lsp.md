# Cx — Language server

`cx lsp` speaks JSON-RPC 2.0 over stdio (Content-Length framing). The server
shares the exact parser + symbol table as the transpiler, so diagnostics and
navigation cannot diverge.

Implemented:

- lifecycle: `initialize` / `initialized` / `shutdown` / `exit`;
- `textDocument/publishDiagnostics` on `didOpen` / `didChange` / `didClose`
  (full sync, `textDocumentSync: 1`);
- `documentSymbol`, `definition`, `declaration`, `hover`, `completion`,
  `signatureHelp`, `documentHighlight`, `references`, `rename`.

The semantic features reparse the stored document through the shared parser +
sema. `documentHighlight` / `references` / `rename` are **lexical**: they scan
the same file for whole-word occurrences of the identifier under the cursor,
skipping comments and string/char literals (`references` answers `[]` when there
are none, `documentHighlight` reports `kind: 1`, and `rename` returns a
`WorkspaceEdit` whose single-file `changes` map lists one `{range, newText}` per
occurrence). Cross-file `references` and a binding-aware `rename` are not
implemented.

## Resolution order

For `definition` / hover:

1. **Word under the cursor through the symbol table**, preferring a macro origin
   (for symbols generated by `macro_rules!`, `CxMacroMap` records a
   generated-name → macro-definition origin).
2. **A `Type::method` pair around the cursor** — lowered to `Type__method` (a
   generated function) or resolved as a `Trait::method` reference to the trait
   method declaration. `gd` on `new` in `IntMap::new()` jumps to the `new` token
   in the macro body; `gd` on `a` in `A::a` jumps to `a` in `trait A`.
3. **A `recv.method` / `recv->method` member access** — the receiver's type (a
   local/parameter, or a global) resolves it to `Type__method`, else to the
   struct **field**'s declarator, a **trait vtable pointer** (jumping to the
   trait), or a trait method through the pointer (`recv.Trait->method`).
4. **A `macro_rules!` invocation at the cursor**
   (`cx_macro_map_find_invocation`) — `gd` on `define_int_map!` jumps to the
   `macro_rules!` definition.
5. **The innermost named AST node** (`cx_lsp_node_at` walks the tree
   unconditionally and matches on the node's own span).

`definition` follows symbols into imported files (the URI comes from the
symbol's source file).

## Hover

Hover resolves the same `Type::method` / `Trait::method` pair plus a
`recv.method` member (via the receiver's type) and renders the full signature
(`ret Type::method(params)`), preceded by the `//` doc comment above the
declaration (`cx_lsp_doc_above`). A `recv.field` hovers as `<type> <field>`, a
trait pointer as ``trait `T` (vtable pointer on `S`)``, and a local/parameter as
`<type> <name>`.

## Completion

- The general list offers symbol-table names (functions, structs, globals) plus
  keywords, filtered by the typed prefix. Macro-generated `A__B` names are shown
  as `A::B`.
- `recv.` / `recv->` offers the receiver type's members: instance methods
  (`Type__member`, resolved from `s->decl`), the struct's **fields**, and its
  **trait vtable pointers**.
- `recv.Trait->` offers the trait's required methods.
- After `Type::` the list shows the generated members as `Type::method`
  (`insertText` = the bare member).

Completion caveats: plain **prefix** match (no fuzzy matching or auto-import);
only symbol-table entries are offered — **locals/parameters aren't in the
table**, so the *general* list omits them (they do drive `recv.` method
completion via `cx_lsp_receiver_base`); trigger characters are `.` / `:` / `>`,
and `recv.` / `recv->` offers the receiver type's methods, fields and trait
pointers (fields are read straight from the struct's AST declaration).

## Signature help

`textDocument/signatureHelp` (trigger characters `(` and `,`) finds the call's
argument list (`cx_lsp_call_open_at` in `nav.c`), resolves the callee — `f`,
`Type::method`, `recv.method` / `recv->method` — to `Type__method`, and renders
the parameter list with the active parameter (dropping a `.`-method's hidden
receiver).

## Receiver-type recovery on incomplete code

The receiver's type is resolved by `cx_lsp_receiver_base` (in `nav.c`): it uses
`cx_sema_receiver_type` (the enclosing body's parameters and the locals visible
at the cursor, honouring block scope, else a global) and, when that fails
because the live text is an **incomplete expression at the cursor** (typing
`list.` makes the enclosing function fail to reduce, so the local's declaration
is not in the AST), it reparses a copy of the document with the cursor's line
completed by `__cx;` — the declarations *before* the cursor are untouched, so
`list`'s declared type is recovered. `cx_sema_receiver_type` also types `self`
(the enclosing struct) inside a constructor/destructor/`implements` method body,
so `self.` completes/hovers/`gd`s the same way.

## Known limitations

- `gd` on a macro invocation in an imported `.hx` module can land in the wrong
  file or report an invalid cursor line; see [`roadmap.md`](./roadmap.md)
  *Known issues*.
- Cross-file `references` and a binding-aware `rename` are not implemented.
- `positionEncoding` is not negotiated (columns are byte offsets).
- Macro definitions are not indexed (they are gone before the AST is built).
